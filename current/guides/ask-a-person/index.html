    Ask a person¶

    A host-run request verifier records a question and ends its attempt suspended with reason request. The controller exits. The next answer starts one successor on the retained workspace, settles the held request, and continues without rerunning earlier nodes or restoring local/direct workspace files. Agents remain non-interactive.

    This graph asks for approval after each worker pass; a failed worker pass ends the run as worker_failed without asking. Rejection sends feedback to the next pass; approval ends successfully. The graph routes the request's existing timeout error to a failure. The example is an ordinary custom graph; there is no built-in approval template.

    Validate the files, then start the graph in your repository:

    zeroshot run --title "Handle empty search results" --graph graph.json --input input.json --runtime-config runtime.json --validate-only
zeroshot run --title "Handle empty search results" --graph graph.json --input input.json --runtime-config runtime.json
zeroshot inbox list --limit 50
zeroshot inbox show RUN_ID
zeroshot answer RUN_ID --input answer.json

    For approval, change the answer's decision to approved and give empty feedback. An answer must provide every declared signal and every required output field. Unknown fields, signals and labels are refused as invalid_request, naming the path, without consuming the request. A second answer names the accepted successor. resume, including checkpoint selection, refuses requests and names answer before resolving credentials; after an answer it names the successor instead. If that successor fails or is lost, resume on it starts again right after the answer: the request stays answered, the question is not asked again, and node_instance agents continue their conversations from when the question was asked. Only a successor lost in the instant it starts, before its starting point is recorded, restarts at the root with new conversations and asks again.

    Every request has a deadline: timeoutMs from creation, 7 days when omitted, at most 30 days. Acceptance is strictly before the deadline. At or after it, answer checks expiry before content, records an expiry vector and starts the timeout successor, then exits 1 naming it. Without a guard on the request node's timeout error, an expiry continues with the next node like any other unrouted node error; a graph in which a late answer must not proceed routes it, as the example does. Local and direct targets have no request timer. Inbox reads report overdue requests as expired without changing the suspended run or starting anything.

    inbox list returns requests and optional nextAfter in run ID order. Pass that cursor with --after, which locally must be a run ID; --limit accepts 1 through 100, default 50. Answered and force-stopped requests drop from the list. inbox show retains their answered, expired or stopped disposition and the successor link. It shows only the question that run made, never an inherited question.

    Use vectors RUN_ID for bounded summaries and vectors show RUN_ID ID for full requests and answers. Successors inherit the ordered record. checkpoints includes entry to the request node. The run viewer and list display the question, deadline and successor; answering uses the CLI or SDK.

    Request nodes use builtin.request.ask@1 with {"kind":"request"}. They must be verifiers with exactly one required string input text, a flat record output of boolean, integer, number, string or enum fields, the fixed message diagnostic, no instructions and one attempt. They may appear in sequences, choices and loops, including repeated nodes, but never below parallel or map groups. Request nodes in one graph may declare different signals and outputs. Each answer is checked against the node that asked. Workspace checkpoints must be enabled. Stack profiles cannot contain requests.

    Add --target NAME to answer and either inbox command for a named target. Discovery must advertise request_ask: {"kind":"openengine.request-ask/v1"}. Answers use the same resume route and fresh connection authorization as resume; --forward-gh-token has the same meaning. Hosted inbox routes use the separate hosted_inbox extension (openengine.hosted-inbox/v1). A target without those routes refuses inbox reads. Vector reads still require only openengine.run-vectors/v1.

    The Python SDK exposes Client.inbox(after, limit), Run.request() and Run.answer(answer); RunStatus.request carries the question. See the Python SDK guide.
