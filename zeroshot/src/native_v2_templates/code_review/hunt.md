The goal is not to audit every line but to work out what this change can break, including effects outside the edited files. `summary` and `units` describe the change, and its diff against the merge base shows all of it. Read the changed code and what it touches: callers, callees, types, configuration, stored data and tests. On a large change, start with the code most likely to fail in your area rather than trying to read everything.

Report a problem only with a concrete scenario grounded in the code: the input or sequence of events, the path it takes through the code, and the wrong result, crash, data loss, security exposure or broken workflow it causes. A plausible story is not enough. Report every problem you can support this way, including problems in existing code that this change triggers or relies on (say that they predate the change). Other reviewers cover the other kinds of failure. Return an empty list if you find none.
