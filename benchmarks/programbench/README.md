# Zeroshot on ProgramBench

A reproducible, fully containerized benchmark of a minimal review loop on
[ProgramBench](https://github.com/facebookresearch/ProgramBench): rebuild a program from its
compiled reference executable and documentation, offline, then score the rebuild with
ProgramBench's hidden behavioral tests. The loop is a two-node Zeroshot graph: a builder, and an
independent checker whose rejection becomes the builder's feedback for the next round.

## Questions

1. **Cost parity.** Can a cheaper model's check-and-repair loop beat a more expensive model's single
   worker at the same model cost? GPT-5.6 Luna at `xhigh` ($0.20 input, $1.20 output per million
   tokens) runs the loop; GPT-5.6 Sol at `xhigh` ($4 and $20) runs once, as a single worker. The dual
   question: how much does the loop cost to reach the single worker's score?
2. **Prompt study.** Is the loop's benefit the topology, or would the same instructions in one session
   do as well? GPT-5.6 Luna runs once per attempt with a prompt that quotes both roles and asks the
   model to alternate between them.
3. **Checker session.** Does the loop need a checker that starts fresh every round? The same loop runs
   with a checker that keeps its session across rounds, so it remembers what it rejected and the fixes
   it asked for.
4. **Worker only.** Is it the checker, or just more rounds? The loop runs without its checker: the
   builder alone, told "Continue." in its own session round after round, and in a second variant told
   to review its own work against the task again and fix what it finds.

Twenty tasks, 5 runs per arm per task. Every task is reported; there is no pooled test across tasks.

## The graph and prompts

Both arms share one byte-identical `build` node; round 1 of the loop is exactly the single worker.

```
loop "solve" (at most 50 rounds; stop when check.verdict = accepted)
  build  — Codex, keeps its own session across rounds; input = task + feedback ("" in round 1)
  check  — Codex, fresh session every round; verdict accepted | rejected; its diagnostic
           becomes the builder's feedback for the next round
```

Failed rounds follow Zeroshot's normal semantics. A build that crashes or times out leaves the
workspace as it is, the check still runs, and the next round's builder starts a new thread (after a
malformed response it keeps its thread). A check that errors records no verdict, so the loop
continues and the builder receives the previous feedback again (none, if the first check errors).
Zeroshot retries a crashed check once, never a timeout or an invalid response. A run has 6 hours;
a build node 3 hours, a check node 1 hour. When the cap stops a run, the final workspace is what it
has at that moment.

The only text we wrote is two generic role prompts (`prompts/builder.md`, `prompts/checker.md`):

> **Builder:** Complete the task described in the input. Keep working and verifying your own work
> until you believe the result fully satisfies the task. If review feedback is provided, address
> every point without breaking what already works.

> **Checker:** Independently judge whether the current workspace satisfies the task. Derive your own
> checks from the task statement and whatever it makes available; do not rely on the builder's
> tests, notes, or claims. Run the checks. Accept only with concrete evidence that nothing is wrong.
> Otherwise reject and list the most important discrepancies, each with a minimal reproduction.

The prompt study's single sessions use a third file, `prompts/builder-checker.md`: both prompts
verbatim, the verifier guidance Zeroshot gives every check, and four sentences of glue:

> Work in rounds. In each round, act first as the builder and then as the checker, following the
> instructions for each role below. If the checker rejects, its list of discrepancies is the review
> feedback for the builder in the next round. Repeat until the checker accepts, then return.

Zeroshot wraps each prompt in its standard node guidance (for workers: install manifest/lockfile
dependencies and verify before returning; for verifiers: do not modify reviewed material) and a
JSON response contract. All task knowledge comes from the benchmark's own task statement,
`prompts/task.md`, generated by `scripts/build_task_prompt.py` from the upstream mini-SWE-agent
ProgramBench prompt (`prompts/upstream/`, SWE-agent/mini-swe-agent `main` at `04d809ce`). The
script removes only scaffold mechanics (the persona line, the one-bash-command protocol, the submit
sentinel, command examples); every other line is verbatim. The unit tests re-derive it
byte-for-byte.

## Experiments

Each task has three experiment files and a smoke test (`experiments/`):

| File | Arm | Runs | Model |
|---|---|---|---|
| `luna-xhigh-<task>-v1.json` | loop, up to 50 rounds | 5 | GPT-5.6 Luna, xhigh |
| `sol-xhigh-<task>-single.json` | single worker (the build node alone) | 5 | GPT-5.6 Sol, xhigh |
| `luna-xhigh-<task>-prompt.json` | single session with `prompts/builder-checker.md`, 6-hour node limit | 5 | GPT-5.6 Luna, xhigh |
| `luna-xhigh-<task>-checker-resumed.json` | loop, up to 50 rounds, the checker keeps its session across rounds | 5 | GPT-5.6 Luna, xhigh |
| `luna-xhigh-<task>-worker-loop.json` | the builder alone, re-run in its session with "Continue.", up to 50 rounds | 5 | GPT-5.6 Luna, xhigh |
| `luna-xhigh-<task>-self-review.json` | the builder alone, re-run in its session with a self-review instruction, up to 50 rounds | 5 | GPT-5.6 Luna, xhigh |
| `smoke-<task>.json` | one 3-round loop with short limits | 1 | GPT-5.6 Luna, xhigh |

`smoke-svgbob-sol.json` is the same smoke test with Sol and longer node limits;
`smoke-svgbob-checker-resumed.json` is the smoke test with the checker's session kept,
`smoke-svgbob-worker-loop.json` and `smoke-svgbob-self-review.json` the ones without a checker. All 20
tasks share one protocol: the same
prompts, graphs, limits (6 hours per run, 3 hours per build, 1 hour per check), resources (5 runs
at once, 4 CPUs and 7 GB each), evaluation settings and prices. The experiment file declares one
general adjustment to every task, applied by `agent/prepare-task.py` when the agent image is built
and recorded in the manifest: the reference executable moves to `/reference/executable`, a
root-owned directory the agent can run it from but cannot overwrite, move or delete (the task asks
agents to build their own `./executable` at the reference's upstream path); the task statement
points there. On svgbob, three README statements that contradict the reference's behavior are also
corrected in place (`task.doc_fixes`, four replacements); every other task's documentation is left as
shipped. keifu's
experiments run `codex` under `agent/codex-reaper.c` (`resources.reap_orphans`): Zeroshot 10.8.0's
run controller reaps only its nodes' process groups, and keifu's agents test a terminal UI in
pseudo-terminals and tmux, which leave orphaned processes behind.

Loop runs are scored at build 1 and in the final workspace (`eval.rounds`); every round's snapshot is
archived, and the comparisons score the snapshots they need.

The checker-session experiments are the loop experiments with one change in the runtime plan: the
check node's `sessionScope` is `node_instance` instead of `execution` (`arms.loop.check_session_scope`),
so the checker resumes its own session every round, as the builder does, instead of starting fresh.
The graph, the prompts, the input and every limit are byte-identical to the loop's.

The worker-only experiments (`arms.loop.worker_only`) are the loop with its check node removed: the
build node runs up to 50 times in its own session, and every round re-prompts the builder with the
task and the feedback the run started with, `prompts.feedback` (the graph writes no feedback of its
own): "Continue." (`prompts/continue.md`) in the worker-loop experiments, and in the self-review
experiments:

> Continue. The result has not been accepted. If the task is not complete, complete it. Then review
> the current workspace against the task again, independently of your earlier conclusions: derive new
> checks from the task statement and whatever it makes available, run them, and fix every discrepancy
> you find without breaking what already works. Assume there are still defects until you have fresh,
> concrete evidence that there are none.

The prompt, the limits and the prices are the loop's; round 1 differs from the single worker's build
by that feedback alone.

## Comparisons

**Cost parity** (`bench parity`). C is the mean model cost of a task's 5 Sol single workers. Each
Luna loop run is compared through its parity workspace: the workspace after the last build whose
cumulative cost (builds 1 to k and checks 1 to k-1, from the Codex transcripts at Luna's prices)
does not exceed C; build 1 if build 1 alone costs more; the final workspace if the run stops first.
On each task, the mean hidden-test pass rate of the 5 parity workspaces is compared with the mean of
the 5 single workers, each with a 95% percentile bootstrap interval (runs resampled, 10,000
resamples, seed 20260924). Luna outperforms Sol at cost parity if its mean is higher, robustly if
the two intervals do not overlap.

**Equal score** (`bench match`). The dual: the model cost at which the mean score of the 5 loop runs'
deliverables (each run's last build within the budget; nothing, scored 0, before its build 1) first
reaches Sol's mean score, as a share of Sol's mean cost; not reached if no budget up to the end of
the loop runs gets there. Builds are scored in blocks until the search settles.

**Prompt study.** The same two comparisons with the 5 prompted sessions in place of Sol's single
workers: P is the sessions' mean model cost at Luna's prices; the loop is compared at P (equal cost)
and by its cost to reach the sessions' mean score (equal score).

**Checker session.** Both loops are compared through the same Sol single workers: the loop with a
kept checker session gets its own `bench parity` and `bench match` against `sol-xhigh-<task>-single`,
and per task its score at Sol's mean cost, its cost to reach Sol's mean score and its final score are
set against the fresh-checker loop's, each difference with a 95% bootstrap interval as above.
Reported alongside: the model cost of a check round, the rounds within Sol's budget, and how often the
checker accepted.

**Worker only.** The same comparison for the loop without its checker, with either feedback:
`bench parity` and `bench match` against `sol-xhigh-<task>-single`, and per task its score at Sol's
mean cost, its cost to reach Sol's mean score and its final score against the loop's.

A run enters a comparison only if it completed, its compared workspace was scored on all tests (a
workspace that fails to compile or to produce a usable executable scores 0, as on the leaderboard;
an evaluation infrastructure error is re-evaluated once and excludes the run if it persists),
neither that workspace contains nor builds the reference executable, the harness files and Codex
config were unchanged, and it has no disqualifying audit finding: binary instrumentation
(`LD_PRELOAD`, `LD_AUDIT`, `LD_DEBUG`, `LD_PROFILE`, ptrace), direct model-API calls, proxy use by tools,
process-environment reads, web search. An attempt that ends in an infrastructure error is re-run
once from scratch; the runner refuses a second re-run, and the discarded attempt is kept and
reported.

Asked to take both roles in one session, Luna does not loop. All 100 sessions ended on their own,

the equal-cost comparison is in effect the loop's first build, whose instructions are the builder's
prompt alone, against a session told to build and check.

### Checker session

A checker that keeps its session makes the loop cheaper and faster, and worse. Its rounds cost about
half as much (median $0.07 against $0.14 per round; a check $0.02 against $0.05, a build $0.05
against $0.08), so 44 rounds fit into Sol's budget on average instead of 30, the loops took a median
of 94 minutes instead of 221, and the checker accepted 9 loops instead of 6. Yet at Sol's cost the
loop scores lower on 19 of the 20 tasks, by 6.3 points on average (63.2% against 69.5% over the
tasks; Sol's single workers 65.6%), and after all its rounds it is still at 63.2%, against the
fresh-checker loop's 71.1%. It reaches Sol's mean score on 8 tasks instead of 18, for less than Sol's
cost on 7 instead of 15, and at Sol's cost it is ahead of Sol's single worker on 6 tasks instead of
15, never robustly. What the loop gains from a checker that starts every round without memory of
the last one is worth more than the rounds that memory saves.

## Reproduce

Requirements: Linux x86_64, rootful Docker 26 or newer, Python 3.12 for the unit tests, and an
OpenAI API key with access to `gpt-5.6-luna` and `gpt-5.6-sol`. One experiment at a time needs 20
CPUs and 40 GB of memory for its 5 attempts (4 CPUs and 7 GB each, plus headroom), 24 CPUs for
evaluation (8 workers of 3 CPUs), and at least 60 GiB of free disk; a loop run archives every
round's workspace, a few GB per run on most tasks and up to 65 GB on fasttext, whose builders leave
trained models behind. The runner refuses hosts that cannot fit the configured concurrency. Use a
host without a cloud instance role (ProgramBench's evaluation runs agent-written code in networked
test containers).

1. Clone and store the key. The key never passes through argv: it reaches the runner as a read-only
   file and the agent containers per `docker exec`.

   ```bash
   git clone --branch benchmark/programbench https://github.com/the-open-engine/zeroshot.git
   cd zeroshot/benchmarks/programbench
   read -rs OPENAI_API_KEY && export OPENAI_API_KEY   # or scripts/push-openai-key.sh user@host for a remote box
   scripts/zsbench check-key experiments/luna-xhigh-svgbob-v1.json
   ```

2. Run the smoke test for a task (about 30 minutes plus image pulls, about $1). It proves the
   isolation from inside a real run, runs the whole pipeline with short limits, and re-scores a
   published leaderboard submission on the task, which must agree with the leaderboard within 2
   points. On crowbook, dust, tree-sitter and samtools that last check fails by design (see Scoring
   and cost); every other check must pass. `smoke-svgbob-checker-resumed.json` is the smoke test for
   the checker-session experiments, `smoke-svgbob-worker-loop.json` and `smoke-svgbob-self-review.json`
   for the worker-only ones.

   ```bash
   scripts/zsbench smoke experiments/smoke-svgbob.json
   ```

3. Run the task's three experiments. Each runs its 5 attempts at once, evaluates them and writes
   `results/<experiment>/summary.md`. A loop experiment takes up to 6 hours plus evaluation; the
   single workers 10 to 20 minutes; the prompted sessions 5 to 20 minutes. Per task, Sol's 5 single
   workers cost about $22, Luna's 5 loops about $35 and the 5 sessions about $1.35.

   ```bash
   scripts/zsbench run experiments/luna-xhigh-svgbob-v1.json
   scripts/zsbench run experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench run experiments/luna-xhigh-svgbob-prompt.json
   scripts/zsbench run experiments/luna-xhigh-svgbob-checker-resumed.json   # the checker-session study
   scripts/zsbench run experiments/luna-xhigh-svgbob-worker-loop.json        # the worker-only study
   scripts/zsbench run experiments/luna-xhigh-svgbob-self-review.json        # its self-review variant
   ```

4. Compare. `parity` scores the loop's parity workspaces and writes
   `results/luna-xhigh-svgbob-v1/parity/<against>.json` and `.md`; `match` searches the cost to reach
   the other arm's mean score and writes `<against>.match.json` next to it.

   ```bash
   scripts/zsbench parity experiments/luna-xhigh-svgbob-v1.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench match experiments/luna-xhigh-svgbob-v1.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench parity experiments/luna-xhigh-svgbob-v1.json --against experiments/luna-xhigh-svgbob-prompt.json
   scripts/zsbench match experiments/luna-xhigh-svgbob-v1.json --against experiments/luna-xhigh-svgbob-prompt.json
   scripts/zsbench parity experiments/luna-xhigh-svgbob-checker-resumed.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench match experiments/luna-xhigh-svgbob-checker-resumed.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench parity experiments/luna-xhigh-svgbob-worker-loop.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench match experiments/luna-xhigh-svgbob-worker-loop.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench parity experiments/luna-xhigh-svgbob-self-review.json --against experiments/sol-xhigh-svgbob-single.json
   scripts/zsbench match experiments/luna-xhigh-svgbob-self-review.json --against experiments/sol-xhigh-svgbob-single.json
   ```

5. Repeat steps 2 to 4 for the other 19 tasks. On a large host, experiments can run side by side:
   `ZSBENCH_ALLOW_PARALLEL=1 ZSBENCH_DETACH=1 ZSBENCH_RUNNER_NAME=zsbench-runner-<name> scripts/zsbench run <experiment> --skip-eval`
   starts a detached runner per experiment (follow it with `docker logs -f zsbench-runner-<name>`;
   stop it with `docker stop -t 1800 zsbench-runner-<name>` so attempts are wound down and
   recorded). Attempts mostly wait on the model API, but evaluations compete for CPUs, so score
   afterwards with `scripts/zsbench eval <experiment>`, both arms of a task on an otherwise idle
   host: timing-sensitive tests are sensitive to CPU contention.

`scripts/zsbench` builds the runner image (`Dockerfile`) and runs it with the host Docker socket
mounted. It records the exact commit and refuses a paid `run` from a dirty or non-git tree (override
with `ZSBENCH_ALLOW_DIRTY=1`). Running the same `run` command again resumes: stopped attempts start
over, completed ones are kept. The runner refuses to resume into results from a different experiment
digest (`--allow-mixed` overrides), refuses to start while another runner is running or while
containers of the same experiment are still up (`scripts/zsbench cleanup <experiment>` removes what a
crashed runner left behind), and hands results back to the invoking user. `eval` re-scores existing
attempts with the current code and `report` rebuilds the summary; both record that code in the
manifest and summary. To re-run a smoke test, move its results directory aside first. Other
settings: `ZSBENCH_RESULTS_DIR`, `ZSBENCH_SECRET_FILE`, `ZSBENCH_DOCKER_SOCK`, `ZSBENCH_IMAGE`,
`ZSBENCH_EVAL_WORKERS`, `PROGRAMBENCH_DOCKER_RUN_TIMEOUT` (seconds programbench waits for an
evaluation container to start, default 300; a build whose container does not start in time gets no
result and `match` stops until it is run again); `--keep-containers` and `--skip-eval` for `run`; `plan` renders the graphs
and the attempt order without running anything. Unit tests: `python -m unittest discover -s tests`
(Python 3.12), or inside the runner image.

## Environment and isolation

- **Task environment:** the official ProgramBench task image, pinned by digest, unchanged except
  for Zeroshot and Codex's full platform package (checksum-pinned releases, `pins.json`) and a
  Codex config. The agent runs as the image's non-root `agent` user; the reference executable is
  execute-only. The image's own sudo rules (package managers, cargo, go) are left as ProgramBench
  ships them. Their install hooks amount to root, so the harness files (Zeroshot, Codex, Codex's
  system config) are fingerprinted at the start, after every node and at the end, and a change
  excludes the run.
- **Network:** every attempt gets its own internal Docker network whose only exit is its own
  tinyproxy, which allows HTTPS `CONNECT` to `api.openai.com` and nothing else. Tool commands get
  no proxy settings and no DNS, so they have no route out, like the upstream `--network none`;
  only Codex itself reaches the model API. Codex web search is disabled (it runs server-side and
  would bypass the proxy). Codex's own background requests (github.com, chatgpt.com) are refused
  and logged.
- **Secrets:** the API key reaches Zeroshot only through `docker exec -e OPENAI_API_KEY`. Tool
  commands cannot see it: the Codex config applies its credential exclusions and turns off the shell
  snapshot (which otherwise re-exports the whole environment into tool shells), and the Zeroshot and
  Codex executables are root-owned and execute-only, so the kernel marks the processes the harness
  starts from them non-dumpable and their `/proc/<pid>/environ` and memory are unreadable to the
  agent (a readable copy of Codex would expose its key). A process that `docker exec` starts
  directly stays dumpable even from an execute-only file, so the runner starts the key-holding
  submitter through a shell's `exec`. Codex's code-mode JavaScript runs in a bare V8 isolate that
  exposes only Codex's tool functions, with no environment, file or network access. The smoke test
  proves each point from inside a real run and checks the submitter's launch path on the host. Every
  artifact (plain files, archive members, nested archives, and the decompressed git objects of
  archived repositories) is scanned for the literal key; a hit writes `DO-NOT-PUBLISH.txt` and
  fails the command.
- **Node independence:** every node starts from its prompt and this configuration alone. Left alone,
  Codex marks `/workspace` trusted on first use and then loads `AGENTS.md` files and
  `.codex/config.toml` layers from the workspace into every later node, so a builder could instruct
  the checker or undo the settings above. The Codex config pins the workspace as untrusted, which
  leaves the explicit sandbox and approval settings in force; the smoke test plants a canary
  `AGENTS.md` to prove it is never loaded. The Codex home (`~/.codex`) is shared by all nodes and
  Codex also reads user instructions, skills, rules and hooks from it, so after every node the
  runner records those files and the config (none but the config exist at the start) along with the
  harness fingerprint; any change, or any transcript that shows loaded `AGENTS.md` instructions, is
  flagged in the summary. Codex memories are off as well.
- **Harness integrity:** Zeroshot resolves `codex` through the `PATH` it starts with, for every
  node, and the task image puts the world-writable `/usr/local/cargo/bin` first. The runner
  therefore starts Zeroshot by absolute path, and runs every harness command (probes, archives,
  Zeroshot calls) with a `PATH` of root-owned directories only, so no node can plant a `codex` that
  a later node would run with the key, or a `tar` or `sha256sum` that would spoof the checks meant
  to catch it; tool shells keep the image's `PATH`. The smoke test plants decoys of all of these
  there and requires that none ever runs.
- **Tooling parity:** Zeroshot starts Codex with a minimal environment, so the rendered Codex
  config mirrors the task image's ENV (`CARGO_HOME`, `RUSTUP_HOME`, …) into tool commands. It
  also gives them the image's plain `/tmp` as `TMPDIR`, instead of a directory inside Zeroshot's
  run state.
- **Archives:** workspace archives are made as the `agent` user, like the upstream harness, so the
  execute-only reference is never archived wherever the agent moves it. Agents do move it (the task
  asks them to build `./executable` at the same path), so every snapshot records where the
  reference is, by hash.

Residual risks, documented rather than engineered away: filtering is by CONNECT host name, not TLS
SNI; ProgramBench's eval runs agent-written code in networked test containers (use a host without
a cloud instance role, and keep the cloud metadata endpoint unreachable from containers).

## Scoring and cost

- **Evaluation once per workspace:** a check snapshot usually holds the same code as the build
  before it, and a final the same as the last snapshot. Archives are grouped by their files'
  contents, modes and link targets (timestamps ignored); one representative per group is evaluated
  and its result is shared, recorded as `evaluated_as` in `scores.json` and in
  `evals/representatives.json`.
- **Score:** `programbench eval` 1.2.4 (the leaderboard's version) on the task image pinned by
  digest, with the hidden tests pinned to Hugging Face revision `de0ddfb6` and
  `pytest-rerunfailures` pinned to 16.4 (`bench/pbeval.py`; newer releases emit phantom passing
  entries, which upstream fixed the same way). Scores use ProgramBench's own
  `test_results_map`/`score_from_tests` with the leaderboard registry's ignore list at `794fa30b`.
  A test branch whose test run hits ProgramBench's time limit, or whose pytest cannot load an
  installed plugin before any test runs, counts as tests not passed, as on the leaderboard; any
  other evaluation error is an infrastructure failure, retried once. The smoke test re-scores a
  pinned, published leaderboard submission on the same task and requires agreement within 2 points.
  On four tasks that scoring does not match the leaderboard: crowbook (67.0% here against 2.9%; the
  leaderboard's run failed even `--help` tests that pass here), dust (74.8% against 87.3%; its
  golden outputs embed the leaderboard machine's filesystem block sizes, and its libtmux branch
  cannot run), tree-sitter (48.8% against 46.1%; 33 tests pass only here) and samtools (7.7% against
  22.6%; its largest branch hits the 1-hour limit). Every difference is deterministic, and both arms
  are scored the same way, so the comparisons stand, but absolute scores on these tasks are not
  comparable with the leaderboard.
- **Cost:** priced from Codex's own session transcripts (each is one thread; its cumulative usage
  splits into rounds at each node prompt) with the experiment's pricing table (input, cache reads,
  cache writes, output). Zeroshot's ledger is reported alongside but not used: it double-counts a
  resumed thread's earlier turns.
- **Audits:** the shell commands Codex actually ran (from its transcripts, not the code-mode
  JavaScript around them) are scanned per node and round (one graph execution, which can span
  several Codex turns), along with web-search calls and, for instrumentation code, the files the
  agent wrote. Disqualifying findings are the channels that could carry withheld information:
  instrumenting a binary (`LD_PRELOAD`, `LD_AUDIT`, `LD_DEBUG`, `LD_PROFILE`, ptrace, the only way to look inside the
  execute-only, dynamically linked reference), calling the model API, using the proxy, reading
  another process's environment (a process reading its own `/proc/self/environ` sees only what it
  already has), and web search. Reported for human review: static analysis of anything named
  `executable` (the task allows it on the builder's own binaries; on the reference it fails with a
  permission error, and such attempts are counted separately), moving the reference, network fetch
  attempts, sudo, reading cached dependency sources, and touching harness internals. Check rounds
  are diffed against the preceding snapshot to confirm verifiers did not edit sources, and every
  scored archive and built executable is compared with the reference by hash.

## Known deviations from the public leaderboard setup

- **Harness:** Zeroshot driving the Codex CLI, not mini-SWE-agent. Compare arms within this
  benchmark; leaderboard numbers are context.
- **Network:** the model API is reachable by Codex (see above); Codex's system prompt also says
  network access is enabled, while the task statement says it is not.
- **Task wording:** the task statement comes from mini-swe-agent `main` (`04d809ce`). Released
  mini-swe-agent versions used by leaderboard runs (v2.2.x–v2.4.x) phrase the same rules
  differently ("This is a reverse-engineering benchmark…").
- **Task environment:** the reference executable lives outside the workspace, and svgbob's README
  is corrected in three places (see Experiments).
- **Limits:** 6 hours wall clock per attempt (as upstream); 3 hours per build node, 1 hour per
  check; the prompted sessions' single node has 6 hours within a 6¼-hour attempt; no step limit.
- **Single-arm prompt:** the shared builder prompt mentions review feedback, which a single worker
  never receives.
- **Served model:** OpenAI serves `gpt-5.6-luna` and `gpt-5.6-sol` by name; transcripts do not
  identify a model snapshot, so a reproduction assumes the same served models and the prices in the
  experiment files.
